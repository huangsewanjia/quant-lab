行业装载变更留痕：diff 日志 + 快照源整源替换

WORK-585 · 数据底座 quantdb · 生成于 2026-11-29 00:21 CST · 目标 runtime：Mo-server

一句话：装载器现在每次替换前先把「库内现状 vs 本次快照」的逐行差异写进 industry_load_diff，再动手替换（同一事务，失败一起回滚）； cnesa_storage 改为整源替换，WORK-577 遗留的 F3（上游删期、库内残留幽灵行）消除； 复核用 v_industry_load_changes_recent 看近 30 天的值变化与被删行。 现有 17 张观测表结构、C1–C8 判据、industry.sh 调用方式一律未改。

1. 用途与受众

给谁用：负责行业层数据的人（复核者），以及任何要引用 industry_* 表之前 想知道「这条数什么时候被人改过」的研究者。

解决什么：旧装载只有 DELETE + INSERT，审计表只记行数与耗时。 上游把某个值改了、或删掉一整期，库内变化没有任何记录——复核者只能看到「行数没变」， 看不到「3.7 亿千瓦变成了别的数」。本单把「替换」变成一件有账可查的事。

不解决什么：不判断变化是否符合业务预期，不做审批流，不发消息；它只保证 「改了什么、删了什么」逐行可读、可追、可复跑。

2. 首次使用（三步）

  1. 确认表在：select count(*) from industry_load_diff; （表由 db/schema_industry.sql 随每次装载自动建立，无需手工执行 DDL）。
  2. 找最近一次运行：select run_id, max(finished_at) from industry_load_audit group by 1 having count(*) = 17 order by 2 desc limit 1;
  3. 看要人复核的变更：select * from v_industry_load_changes_recent order by changed_at desc limit 50;

3. 主流程：装载一次到底发生什么

3.1 差异怎么算

源类型比对键能产出什么
自然主键源（gfex / lpr / cnesa / cninfo / pbc / stats / comtrade / exchange / owid / sne） 表的真实主键（如 period × indicator） value_changed（逐列一行）、row_added、row_dropped
row_hash 主键源（caam / cpca / mof / nea / benchmark / ppi / trendforce） row_hash（内容哈希） row_added / row_dropped：内容改版天然表现为「旧 hash 走、新 hash 来」， indicator 用业务键文本渲染，人一眼能对上

数值按「值」比对（80620 与 80620.0 视为同一个值）， DATE 与零点 TIMESTAMP 规范化到同一天——否则每次重载都会把全表记成「变了」。 这两条是实测踩出来的：首版草稿在真实库上做只读演练时， exchange_daily_quotes 报了 87,024 个假变化。

7. 已知限制

  • 整源替换只给了 cnesa_storage。其余快照型源（benchmark / ppi / trendforce）按 snapshot_date/as_of 分区替换，旧快照按设计保留；它们是否也该整源替换， 要看「同一快照日上游会不会删行」，需要各自的一次实测，不在本单范围。
  • row_hash 源没有「值变化」：内容改版显示为一行 add + 一行 drop。不把两行配成一条， 是因为业务键不唯一（146 行对 98 个业务键），配对靠推断、推断错比不推断更糟。
  • C9 只查留痕完整性，不判断变化是否符合业务预期——那是人看视图的事。
  • history/ 每个抓取批次都会新增一套：哈希覆盖数据 + manifest.json （+ 预测源 article.txt），而 manifest.fetched_at 每次抓取都变，所以不是 「上游不变就不增长」——每天约新增 17 份数据 + 17 份 manifest（当前最大原始文件 2.5 MB，估算 每天 3–5 MB、一年约 1.5 GB）。要限额需另做归档策略，不在本单。
  • diff 不清理：每日/每月累积，量级是「每次装载的变更行数」，正常重跑每表 1 行； 若将来需要保留窗口，另开单做归档，不在本单。
  • --full 的 diff 会放大：清表重装会为被清掉的行各写一条 row_dropped （industry_stats_gov_release 13.7 万行 → 约 27 万条 diff，实测 executemany 约 2,450 行/秒，仅插入约 2 分钟），所以它仍是「排查时用」的手工命令，不进定时任务。
  • 数据库结构：新增 1 表 + 1 视图，17 张观测表零改动；旧版本 DuckDB 客户端读到 industry_load_diff 不影响既有查询。

9.1 表结构

CREATE TABLE IF NOT EXISTS industry_load_diff (
    run_id      VARCHAR NOT NULL,   -- 与 industry_load_audit.run_id 同一次运行
    source      VARCHAR NOT NULL,   -- Source.name
    table_name  VARCHAR NOT NULL,
    period      DATE,               -- 分区日期；非日期分区源为 NULL
    indicator   VARCHAR NOT NULL,   -- 业务键文本 k=v|k=v
    change_type VARCHAR NOT NULL,   -- value_changed | row_added | row_dropped | no_change
    column_name VARCHAR,            -- value_changed 时变化的列名
    old_value   VARCHAR,            -- 原值 / 被删行整行文本；源侧为空记 ∅
    new_value   VARCHAR,            -- 新值 / 新增行整行文本；no_change 存汇总文本
    source_doc  VARCHAR,            -- 对应 URL：该行自己的 source_url / url 列
    reason      VARCHAR NOT NULL,   -- 改动原因：装载模式 + 快照抓取时间 + 变更性质
    changed_at  TIMESTAMP NOT NULL
);
-- 存量表兼容：ALTER ADD COLUMN IF NOT EXISTS + 历史行回填「首版上线前写入」
-- raw 快照留档：raw///history/-.（同内容去重，只增不删）
