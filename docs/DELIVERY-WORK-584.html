4. 主流程：一条预测值怎么进库

4.1 分步操作

  1. 抓取：fetch_cnesa_storage.py 抓一次公开页，to_text 去标签后同时跑观测规则与预测规则；预测命中区间也计入覆盖率，因此 3 个数字不再出现在观测层“未提取”清单。
  2. 落 raw：预测行写 part.parquet；提取用的正文写 article.txt（C8 离线回指的证据）；预测提取失败写 failed.json。
  3. 装载：load 把观测 17 源与预测源分两组；预测组 run_id 带 F 后缀，保证 C5 仍能找到“17 表完整运行”。预测组按 dataset 分区整组替换，撤稿不留残行。
  4. 校验：C8_forecast 查 8 项；scripts/work584_verify.py 从提取到库端到端复核。

9. 已知限制与需要确认

  • 只有 1 个来源、3 条数据。本单按工单范围只做 CNESA；别家预测要新增 dataset 与规则版本，表结构已通用。
  • 预测值不做单位换算。跨源比较（亿千瓦 vs GW）需在查询里换算，表不替你选口径。
  • “能在原文定位”验证到的是去标签后的正文文本（article.txt，与提取同一份 to_text() 输出），不是原始 HTML 字节；原始 HTML 未落盘。若验收口径要求对 HTML 逐字校验，需另存 HTML。
  • 预测表没有新鲜度闸。上游改词导致提取 0 行时，fetch 保留旧 raw 并写 failed.json，表里仍是旧值；C8 不会因此 FAIL。是否需要 staleness 闸属产品口径，本单未擅自加。
  • 全量 pytest 有 1 项与本单无关的既有失败：test_nea_parse.py::test_parse_table_6col_splits_mtd_and_cum（live 树 fetch_nea_power.py 正由 WORK-581 的另一次执行改动；本单 diff 未触及该文件与 NEA 任何代码）。
  • 需要确认（数据口径）：3.7 亿千瓦原文带“以上”，表里按工单要求取 3.7、把“以上”留在 context；若研究上需要“下界”语义，请明确是否新增一列（本单未擅自加）。

11. 附录：表结构（DDL 摘要）

CREATE TABLE IF NOT EXISTS industry_forecast (
    "dataset"            VARCHAR NOT NULL,
    "indicator"          VARCHAR NOT NULL,
    "value"              DOUBLE  NOT NULL,
    "unit"               VARCHAR NOT NULL,
    "period_target"      DATE    NOT NULL,
    "period_target_raw"  VARCHAR NOT NULL,
    "period_target_type" VARCHAR NOT NULL,
    "period_published"   DATE    NOT NULL,
    "source_org"         VARCHAR NOT NULL,
    "source_doc"         VARCHAR NOT NULL,
    "context"            VARCHAR NOT NULL,
    "caliber"            VARCHAR,
    "published_date"     DATE,
    "extracted_at"       TIMESTAMP NOT NULL,
    "rule_version"       VARCHAR NOT NULL,
    PRIMARY KEY ("dataset", "indicator", "period_target", "source_org")
);

目标期编码：calendar_year_end 取该年 12-31；five_year_plan_end 取规划期末年 12-31（十五五 = 2026–2030 → 2030-12-31）。 原文表述存 period_target_raw。列级口径见 db/schema_industry.sql 3.1 节。
