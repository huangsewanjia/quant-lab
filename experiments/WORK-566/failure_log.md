## §1 面板构建期（`scripts/work566_build_panel.py`）

### 1.1 收益序列键名不一致 → 特征层全部为 NaN
- **现象**：首轮 `feat.npy` 的 28 个资产级维度全 NaN。
- **根因**：面板把收益序列存成 `ret/r1.npy`，而特征层按 `r_1` 取；键名 `r1` vs `r_1` 不一致。
- **处置**：统一为 `r_1 / r_5 / r_21 / r_63 / r_126`；`ret/` 目录下残留的 5 个旧名文件
  （`r1.npy` 等，sha256 相同 → 系同一份坏数据被重复写出）**不作为证据**，脚本一律不引用。
- **证据**：`data/WORK-566/meta.json` 的 `files` 段列出全部文件的 sha256。

### 1.2 基础字段字典漏项 → 估值/流动性维度静默变 NaN
- **现象**：`pe_ttm / pb / turnover_rate / turnover_rate_f / log_amount / log_circ_mv`
  六维在样本上恒为 NaN，且**不报错**。
- **根因**：抽取用的字段字典漏载这 6 个键，`dict.get(key, None)` 静默返回 None。
- **处置**：改为「缺键即抛异常」，不再静默降级。
- **证据**：`experiments/WORK-566/panel_audit.json` 的 `dims` 段（逐维 NaN 比例）。

### 1.3 pandas 3.x 移除 `DataFrame.rolling(axis=1)`
- **现象**：`TypeError` 于全部滚动窗口计算。
- **根因**：pandas 3.1.1 移除了 `axis=1` 的 rolling 语义。
- **处置**：转置后沿行滚动（等价，无前视）。

### 1.4 S1 目标 `V^(h)` 的轴方向错 → 波动目标取反
- **现象**：`V5 / V21` 与 `R5 / R21` 的相关性异常接近 1（应为独立量纲）。
- **根因**：协方差矩阵的轴序与标签定义不一致。
- **处置**：改用恒等式 `Σl² − R²/h` 的前缀和实现，不做显式协方差。

### 1.5 `M^(h)`（最大回撤）前视
- **现象**：最大回撤目标使用了区间**之后**的极值 → 标签里含未来信息。
- **根因**：直接对整段窗口取极值。
- **处置**：改为前向 DP `Mx(t,k) = max(lc(t), Mx(t+1,k−1))`，只在窗口内取极值。
- **影响**：这是**会污染训练标签的前视 bug**，若未修则本单全部数值作废。

### 1.6 `trade_cal.cal_date` 是 DATE 类型
- **现象**：`cast(cal_date as int)` 抛转换错误；后改 `cast(cal_date as INTEGER)` 仍失败
  （DuckDB 不支持 DATE → INTEGER 直转）。
- **处置**：统一 `cast(strftime(cal_date,'%Y%m%d') as int)`。
- **同一坑复发于 Stage 0 探针**（§3.4），说明该类型需要跨脚本统一处理。

### 1.7 `stk_limit` 早期空分区列类型为 NULL
- **现象**：`VARCHAR -> NULL` 转换错误。
- **根因**：2017-01-10 等分区为空文件，列类型推断成 NULL。
- **处置**：所有 `read_parquet` 一律加 `union_by_name=true`。

### 1.8 窗口查询全量扫描 → 机械盘上跑到不可用
- **现象**：单个窗口聚合查询在全表上跑。
- **处置**：按 hive 年份分区裁剪（`trade_date=YYYY*/**/*.parquet`），
  实测日频窗口查询 5.7 ~ 16.4 s。

### 1.9 市场级特征写入 `feat.npy` 极慢
- **现象**：900 MB 散写 + 3.1 GB RMW/回写，单步 4 ~ 10 min，进程长期处于 D 态。
- **根因**：共享机器机械盘 I/O 争用（`load average` 8+、swap 占满）。
- **处置**：按维度块写、合并写回；`--skip-extract` / `--skip-features` 支持断点续跑。
  全量面板最终 595 s 建成。

## §2 预注册落地与样本构造期（`scripts/work566_prior.py`）

### 2.1 全部 8 个预测块被跳过（**最严重的一类**）
- **现象**：日志逐行打印「块 b2016: 起点 20160101 不在日历内，跳过」…… 8 块全跳过；
  `prior.json` 里除 `btest` 外全部 `ok:false`。
- **根因**：块起点写成 `20160101 / 20170101 / …`，**1 月 1 日都不是交易日**；
  代码用 `date_index.get(blo)` 精确查日历，查不到就跳过整个块。
- **处置**：改为 `np.searchsorted(cal, blo)` 定位「不早于 blo 的第一个交易日」。
- **若未修**：S2 的年度先验全部缺失，训练会退化成「只有 P 没有先验」，H1 直接无意义。

### 2.2 目标窗跨切分边界的样本未剔除（口径偏离论文）
- **现象**：训练段末尾 21 个交易日的样本，其 21 日结果窗伸进了验证段（2022 年）。
- **根因**：只按样本日切分，没按论文 Table 3 的「Samples whose target windows cross
  split boundaries are excluded」处理。
- **处置**：按「t + 21 < 下一切分首日」剔除。剔除数：训练 88,156 条、验证 106,101 条。
- **影响**：这是**前视泄漏**（训练标签用了验证段的价格）。修后样本量反而更贴近论文：

| 切分 | 本单（修后） | 论文 Table 3 | 差异 |
|---|---|---|---|
| Train | 3,989,422 | 3,883,006 | +2.74% |
| Validation | 2,126,317 | 1,990,842 | +6.81% |
| Test | 2,949,469 | 2,965,433 | **−0.54%** |
| 合计 | 9,065,208 | 8,839,281 | +2.55% |

### 2.3 「截距不惩罚」的岭回归用两步法求解
- **现象**：原写法 `W = (XᵀX+αI)⁻¹XᵀY` 后再补截距，在特征列和 ≈ 0 时才等价；
  而本单标准化后列和**不严格为 0**（剔除非有限样本后有偏）。
- **处置**：改为联立解 `(XᵀX+αI)W + Xᵀ1·c = XᵀY`、`Xᵀ1·W + nc = 1ᵀY`，闭式精确解。

### 2.4 先验拟合池混进了 2013 年的额外历史
- **现象**：窗口起点是 2013-01-04，块 b2016 的拟合池因此含 2013 年样本。
- **根因**：池的下界没有限制。
- **处置**：池下界锁到 `FIT_LO = 20140101`（论文的先验初装切分「2014–2015」）。

### 2.5 全局标准化统计的子样本只有 400 条
- **现象**：日志「每维有效样本 360 ~ 401」。
- **根因**：`step = len(fit_idx)//400`。
- **处置**：子样本改为 20,000 条（每维有效样本 17,541 ~ 20,036）。

## §3 Stage 0 端点探针期（`scripts/work566_data_probe.py`）

### 3.1 第一次跑：分区 glob 用 `+` 而不是 `,`
- **现象**：`Binder Error: Could not bind ... '+'`，全部分窗查询失败。
- **根因**：`read_parquet([...])` 的列表元素分隔符写成了字符串拼接。
- **处置**：`",".join(...)`。
- **代价**：探针整轮报废，重跑一轮（表级覆盖 + 分窗覆盖共约 10 min）。

### 3.2 第二次跑：`cast(ann_date as int)` 不支持 DATE
- **现象**：`Conversion Error: Unimplemented type for cast (DATE -> INTEGER)`，
  探针在**最后一个查询**上失败，前面约 20 min 的表扫描全部白跑。
- **处置**：改 `cast(strftime(ann_date,'%Y%m%d') as int)`。

### 3.3 探针整轮在共享机械盘上跑 20 ~ 30 min
- **现象**：`daily_basic` 单表 `count(distinct ts_code)` 耗时 287 s（另一次 139 s）。
- **根因**：共享机器 I/O 争用。
- **处置**：不降低覆盖面，改用分区裁剪 + 后台跑。

### 3.4 `fina_indicator` 的 PIT 口径实测
- **结论**：`ann_date` 均为 DATE 类型，`ann_date >= end_date` 的比例为 1（as-of 对齐硬条件成立）。
- **但本单**未使用基本面维度**（理由见预注册偏离 #6），故该端点只做探针复测，不进入 40 维。

## §4 回测引擎期（`scripts/work566_backtest.py`）

### 4.1 `traded_notional` 用了日历下标 → IndexError
- **现象**：`IndexError: index 2673 is out of bounds for axis 0 with size 578`。
- **根因**：面板按**日历下标**索引（0 ~ 3270），而 `traded_notional` 按**位置下标**（0 ~ 577）；
  读写混用。
- **处置**：全部改为位置下标 `i`；并做了一次全文 grep 复查（首轮补丁只改了 `+=` 没改读取处，
  第二轮才补上 `turnover[i] = traded_notional[i] / ...`）。

### 4.2 持有期多一天（协议错，**会改变结论**）
- **现象**：`exit_day = i + 1 + H_HOLD`。
- **根因**：把「买入日 = i+1」和「持有 21 日」重复加了一次。
- **论文原文**（附录 G，Eq.35 前一段）：「Predictions based on information through the
  close of session t are executed at the next open, t+1. Each batch maintains fixed
  position units until the close of t+H, where H=21.」
- **处置**：`exit_day` = **日历下标** `dates_sorted[i + H_HOLD]`，即持有到 t+21 收盘。

### 4.3 `exit_day` 混用位置下标与日历下标
- **现象**：`exit_day` 存的是位置（i+22），比较时用的 `day` 是日历下标（≥2670），
  → `day < exit_day` 恒为假，**每个批次会在第一天就被卖掉**。
- **处置**：`exit_day` 统一存日历下标。

### 4.4 批次删除用 `list.remove`（字典相等比较）
- **现象**：两个批次字典内容相同时会删错对象。
- **处置**：改为按身份（`is`）删除。

### 4.5 并列预测值的定序与论文不一致
- **论文原文**：「Ties are resolved by asset order in the prediction file.」
- **原实现**：按 `(-预测值, stock_idx)` 排序 → 并列时按股票代码，与论文不符。
- **处置**：改为**稳定排序只按预测值降序** → 并列保持预测文件中的资产顺序。
  独立复算侧同步改为同一规则（两侧都用论文规则，不互相抄）。

### 4.6 回测整体跑通的口径验证
- **结果**：FMB-style 基线 RankIC **9.38%**（论文 FMB-style 8.76%），
  净 AR 35.52%、净 SR 1.30、MDD −20.08%、557 个批次、
  涨停剔除 170 次、停牌剔除 0 次、顺延卖出 1,161 次、退市清算 31 次。
- **意义**：A 股四项约束全部真实被触发，不是摆设。

## §6 训练期（`scripts/work566_train.py`）

### 6.1 `m_k / v_k` 的 UnboundLocalError（**必崩**）
- **现象**：`losses_on` 内 `m_k = 0.9 * m_k + 0.1 * bm` 使 `m_k` 成为函数局部变量，
  首次调用即 `UnboundLocalError`。
- **处置**：改为 in-place 更新 `m_k.mul_(0.9).add_(bm, alpha=0.1)`，外层张量真正被更新。

### 6.2 读出特征整体载入 → 约 1.8 GB 常驻
- **现象**：`train_readout` 把整个 `u` 读成 tensor（train 1.07 GB + valid 0.72 GB），
  在本机 14 GB 内存、swap 已占满的环境下会被 OOM killer 盯上。
- **处置**：改为**按 batch 从 memmap 取列**；训练集标准化统计仍分块累计。

### 6.3 `mlp_std` 读出分支因重尾列离群值发散（**数值护栏 → 预注册 v1.1**）
- **现象**：冒烟测试里 R0–R3 的验证 SmoothL1 为
  **8514.53 / 9208.30 / 3608.44 / 3594.98**，而 s1_only / s3_only / s1_s2 / full 为
  **0.3526 / 0.3419 / 0.3303 / 0.3549** —— 差 4 个数量级。
- **根因**：`mlp_std`（无 LayerNorm）分支按训练集统计量标准化后，
  重尾列产生 **max|z| = 20.36** 的离群点，直接进入第一层线性 → 预测量级 ~1e2。
  对照组：`full` 带 LayerNorm，不受影响。
- **另一处伪线索（不是根因）**：`P[8..15]`（= `σ^res`）是**块级**统计量，
  训练集标准差只有 1e-6 ~ 2e-5；这类列标准化后 |z| ≈ 1，本身无害。
- **处置**：
  1. 近常数坐标（训练集 std < 1e-8）按 sklearn `StandardScaler` 惯例**不再缩放**；
  2. 标准化后裁剪 **[−8, 8]**（与本单 S1 标准化同常数）。
- **口径影响**：**只作用于 R0–R3**（H4 只报数）；H1（`full` vs `s1_only`）、
  H2、H3 的计算路径**一行未改**。已在 `preregistration_v1.1.md` 落盘并 commit，
  **早于任何 S2/S3 回测产物 commit**。

### 6.4 预测写入的 `(n,1)` 广播错误
- **现象**：`ValueError: could not broadcast input array from shape (19202,1) into shape (19202,)`。
- **根因**：`s1_only` 等臂用的是 `nn.Linear(d_in, 1)`（输出 (n,1)），
  而 `ReadoutMLP` 用了 `.squeeze(-1)`（输出 (n,)）。
- **处置**：统一 `.reshape(-1)`。

### 6.5 S2 编码器在本机 CPU 上太慢（**算力降级外的额外提速**）
- **现象**：冒烟测试 3 个 update + 1 轮验证跑了 6.5 min。
  实测 `nn.TransformerEncoderLayer` 前向只有 **445 ~ 573 samples/s**
  （batch 256，8 线程，i3-12100F，无 AMX）。
- **推算**：全链（2 种子 × S2 训练 + 验证 + 建 u + 读出 + 预测）需 **6 小时以上**。
- **处置**：换成数学等价的 `F.scaled_dot_product_attention` 实现，
  权重沿用官方模块（初始化逐位一致）。
- **等价性证据**（`experiments/WORK-566/fast_encoder_selftest.json`）：
  同一权重下 eval 模式逐元素最大差 **4.768e-07**（float32 舍入量级）→ PASS。
- **提速后**：前向 **4,882 samples/s**（同机实测，3 ~ 11×）。
- **诚实标注**：训练模式下 dropout 的**随机数消费顺序**与官方实现不同
  （两者同为合法 dropout）；种子固定并记录，复现性不受影响。

### 6.6 bfloat16 实测更慢
- **现象**：bf16 前向 1,568 samples/s < fp32 的 4,882 samples/s。
- **根因**：本机 CPU 只有 AVX2，无 AMX / avx512_bf16。
- **处置**：保持 fp32（与预注册 §8 一致）。

### 6.7 读出预测逐臂各读一遍 `u`
- **现象**：8 个臂 × 3 个切分 = 24 趟 `u` 读取（`u` 合计约 4.9 GB），
  memmap 读取是主瓶颈。
- **处置**：改为**每个切分只读一遍、一次写全部 8 臂的预测** → 读取量降为 1/8。
  数值完全一致（同模型、同输入、同算式）。

### 6.8 基础特征读取（向量化 gather）实测不是瓶颈
- **现象**：曾怀疑面板读取拖慢训练。
- **实测**：广播 fancy index **179,591 samples/s**，逐样本连续切片 271,753 samples/s
  → 读取根本不是瓶颈，**模型计算才是**。据此把优化重点放在 §6.5。

## §7 独立复算期（`audit/recompute_work566.py`）

### 7.1 复算侧存在与建模侧**同样**的 off-by-one
- **现象**：`exit_pos = i + 1 + H_HOLD`（与 §4.2 同款错）。
- **为什么严重**：复算脚本与建模脚本**独立编写**，但犯了同一种错 → 两侧「一致」是假一致，
  独立复算就失去意义。
- **处置**：两侧都改成 t+21 收盘。**教训**：协议必须写进两处并交叉核对，
  不能靠「复算一致」来证明协议实现对了。

### 7.2 退市判定混用位置下标与日历下标
- **现象**：`if lb(s) >= 0 and i > lb(s)` —— `lb(s)` 是日历下标，`i` 是位置下标。
- **处置**：改用 `day`（日历下标）。

### 7.3 复算侧漏了预注册要求的「基准调整 alpha」
- **现象**：预注册 §13 要求复算「…/ 相对增量 / 基准调整 alpha」，
  但复算脚本只做了到「相对增量」，**基准调整 alpha 缺项**。
- **处置**：补独立实现（等权基准 + 市值加权基准的日收益序列 → 超额收益 →
  年化 alpha / t 值 / 年化 IR），并加**日历独立核对**
  （用 parquet `trade_cal` 重取的日历确认测试期预测日确实落在日历内）。

### 7.4 复算侧并列定序与建模侧不一致
- **处置**：两侧都按论文「按预测文件中的资产顺序」定序（稳定排序）。

## §8 平台 / 运行环境期

### 8.1 两次 `daemon shut down while task was in flight`
- **现象**：本单前两次 run 在平台侧被打断，**零产出**（无 commit、无 data_probe.json、无预注册）。
- **处置**：改为**每完成一段就 commit + push**，不攒到最后；
  所有长脚本支持断点续跑（`--skip-extract` / `--skip-features`、训练每 100 update 存 checkpoint）。
- **本次 run 的提交序列**（可 `git log` 核）：
  `16b24fb` 预注册 v1.0 → `b49e9c9` Stage2 脚本 → `ca81fdf` 首跑前缺陷修复 →
  `7580a3d` 预注册 v1.1 + 提速 → **（此后才是回测产物）**。

### 8.2 `pkill -f <脚本名>` 误杀自身 shell
- **现象**：`pkill -f work566_data_probe` 把执行该命令的 shell 一起杀了（命令行含同名字符串）。
- **处置**：改为**只按确切 PID kill**，并先 `ps` 核对。

### 8.3 共享机器 I/O 争用
- **现象**：`load average` 8+，swap 7 GB 占满，进程长期 D 态。
- **处置**：并发任务减到最少；重活（面板、训练）与轻活（探针、报告）错峰；
  面板与读出特征一律走 memmap 分块，避免整表进内存。

## §11 训练期 I/O 事故（2026-11-25 13:33 → 15:10）

### 11.1 面板随机取数的 129× 读放大
- **现象**：修复 N2 后重启训练，速度仍只有 0.12–0.63 upd/s（首轮是 1.4），主线程长期 **D 态**。
- **取证**：进程 300 步读了 **33.2GB** 磁盘 = 110MB/步，而有用数据只有 5MB/步。
  隔离复现：单批取数（256 样本 × 126 日 × 40 维 = 4.9MB 有用）实际读盘 **636MB**。
  机制：面板 feat.npy 为 3GB，随机访问时每次 4KB 缺页触发内核默认 **128KB readahead**。
- **A/B（独立进程、先丢缓存）**：默认 → 636.1MB（129.2×）；**MADV_RANDOM → 1.6MB（0.3×）**；
  MADV_SEQUENTIAL → 632.8MB（无效）。
- **踩坑**：第一版 A/B **测法错了** —— `posix_fadvise(DONTNEED)` 对**已映射**的页无效，
  两次跑的都是热缓存，而我又打的是**累计** `read_bytes` 而不是增量 → 结论作废，重测。

### 11.2 预取线程方案失败并移除
- **方案**：后台线程预取下一批面板张量，与主线程前向/反向重叠。
- **失败现象**：两个进程并行启动后 **5.5 分钟没有任何一条更新日志**，CPU 占用 <16%。
- **根因**：**numpy 的二维高级索引 gather 不释放 GIL**，后台线程在 gather 期间持有 GIL，
  主线程被饿死；去掉预取后同机同代码为 0.669s/步。
- **附带 bug**：第一版 Prefetcher 用**单队列**，主线程 `get()` 可能取回刚提交的**原始索引**
  （numpy 数组 → 解包报 "too many values to unpack"）→ 改成输入/输出双队列；
  最终因 GIL 问题**整体移除**。

### 11.3 页缓存留不住 → tmpfs 预置训练日期片（终局方案）
- **背景**：整机可用内存 ~4GB、面板 3GB，且平台自身 `borg` 长期刷盘 → 页缓存留不住；
  磁盘顺序读仅 75MB/s、随机 4KB 缺页 ~5ms → 冷缓存下每批 1,280 次随机缺页 ≈ 6.4s/步。
- **处置**：把 **train 切分所需日期片**（原始下标 [602, 2188)，含 126 日上下文与 21 日未来窗余量，
  **1400MB**）复制到 `/dev/shm`（tmpfs），训练随机取数变 RAM 速；
  验证遍历与 build_reps 改按 **(stock, date) 顺序读**（面板布局为 (stock, date, feat)，
  同一只股的连续日期在磁盘上连续），u 仍写回原行号（日期序）→ 读出分组与取值完全不变。
- **拷贝本身也踩了坑**：用 memmap 逐股切片拷贝 = 无 readahead 的随机读，实测只有 **0.4MB/s**（要 1 小时）；
  改用 `os.pread` 按偏移读 + `POSIX_FADV_SEQUENTIAL` → ~3MB/s，470s 完成。
- **逐位一致性证据**：源文件对应切片与 tmpfs 副本的 **sha256 完全一致**
  （全量 1.4GB 比对：`7bfb0d01bb0329e8a88c45c5eef7f606…`）。
- **修后**：取数 0.0035s/批；两种子**并行**各 1.25 upd/s；
  seed42 前 100 步的 L_anc/L_rev 与上一轮**逐位一致**（确定性复现）。

### 11.5 `_feat_view` 判界 bug：原始日期下标 vs 切片长度

## §12 第二轮独立复审（2026-11-25，审查任务 `bg_c224637b`）

### 12.1 复审结论：B1/N1/N2/N5/N6/N7/N9 均已修，新发现 1 项 BLOCKING（B2）
- **B1 复核**：审计侧插桩实测 `fallback_count=188`、`future_bar_used=0`，退市清算 31 次正常，产物逐位一致。

- **处置**：改为 `u[pos] = ...`，`pos = perm[k:k+B]` 是 **split 内位置**（`perm = np.lexsort((di, si))`，

  与 `y = panel.labels(si, di)`（同为 `idx_all` 序）逐行对齐；
  `perm` 只决定**读盘顺序**（顺序 I/O），不改变行序。读出阶段 `take(u, gi)` / `ytr_t[gi]` 按行取值，
  分组与取值不变 → **无错位**。
- **验证（冒烟）**：`--rep-date-cap 3 --val-stride 64 --max-updates 3` 全链跑通，
  三切分 u 维度均为 **248**（train 2,675 / valid 191 / test 15,276 行），
  8 个臂 ckpt 与预测全部产出，**无 IndexError**。

## §13 整机 OOM —— 本单真正的拦路虎（2026-11-25 16:17）

### 13.1 事实与取证
- **现象**：两个种子的正式训练在 `epoch0 upd500`（16:11:49 / 16:11:45）之后**同时消失**，
  日志无 traceback、无异常、无收尾行（Python 被 SIGKILL 的典型特征）。
- **内核日志（`/var/log/kern.log`，可核对）**：

  ```
  2026-11-25T16:17:48.112419+08:00 Mo-server kernel: minio invoked oom-killer: gfp_mask=0x140cca(...), order=0
  2026-11-25T16:17:48.187820+08:00 Mo-server kernel: oom-kill:constraint=CONSTRAINT_NONE,...,
      task=python,pid=2645946,uid=1000
  2026-11-25T16:17:48.187822+08:00 Mo-server kernel: Out of memory: Killed process 2645946 (python)
      total-vm:7524052kB, anon-rss:1436012kB, file-rss:2920kB, shmem-rss:945184kB
  2026-11-25T16:17:48.153... systemd[1584]: multica-daemon.service: Failed with result 'oom-kill'.
  ```

  同一条日志里还有 **10:47:35 的同型记录**（`Killed process 1534939 (python)` → 同一行
  `multica-daemon.service: Failed with result 'oom-kill'`）。
- **关键结论**：派单卡与平台提示里的「`daemon shut down while task was in flight`」
  **不是平台自身故障，而是整机 OOM 的次生结果** —— OOM killer 同时杀了
  `multica-daemon.service` 和我们的训练进程。触发方是 `minio` 的分配请求
  （`minio invoked oom-killer`），`global_oom`（非 cgroup 限额）。

### 13.2 内存账（为什么我们会被选中）
| 项 | 数值 | 可回收性 |
|---|---|---|
| MemTotal | 15.6 GB | — |
| SwapTotal / SwapFree | 8.0 GB / **0 MB** | **swap 已满 → 无法换出** |
| Shmem（tmpfs 合计） | 3.7–4.1 GB | 其中本单 tmpfs 1.4 GB，**其余约 2.3 GB 属同机其他容器** |
| Cached（页缓存） | 5.2–6.2 GB | 可回收（本单 warm_cache 占 3.5 GB：feat 2.9 GB + targets 0.65 GB） |
| 本单训练进程 anon-rss | **每个 1.4 GB** | 不可回收 |
| 本单 tmpfs 训练日期片 | 1.4 GB（两进程共享） | 需换出才能回收，而 **swap 已满** |

- 硬占用（本单）：双进程并行 = 1.4×2 + 1.4 = **4.2 GB**；swap 为 0 时 tmpfs 等同不可回收内存。

### 13.3 处置：两个种子改**顺序**跑（单进程 6 线程）
- **为什么顺序**：本单训练是**计算受限**（编码器前反向），不是 I/O 受限；
  8 vCPU 上双进程 4 线程合计吞吐 ≈ 单进程 6–8 线程，**总墙钟时间基本不变**；
  但顺序跑把硬占用从 4.2 GB 降到 **2.8 GB**（anon 1.4 + tmpfs 1.4），
  且**前一个种子的产物是安全的**，不会因一次 OOM 全部作废（并行时两个种子一起没）。
- **未改任何协议口径**：batch 256 / 4 epoch × ≤1000 update / 6 epoch × ≤1000 date-group update /
  stock-cap 1000 / val-stride 4 **全部保持预注册 §8 原值**；`--threads`、环境变量
  `MALLOC_ARENA_MAX=2` 属纯算力/内存旋钮，不改变任何取值口径。
- **进程脱离会话**：用 `setsid nohup ... &` 启动（`setsid` 自建 session，
  `ps` 可见 PGID = PID），平台 daemon 重启或被杀**不会**打断训练进程。
- **内存看门狗**：新增 `/tmp/w566_memwatch.sh`（每 10s 记 `MemAvailable/Shmem/Cached/SwapFree/trainRSS`
  到 `/tmp/w566_mem.log`），OOM 前兆可回溯，不再出现「静默消失、无线索」。

### 13.4 仍未关闭的风险
- **swap 满 + 同机他人 tmpfs 2.3 GB**：本单无法控制。若他人 tmpfs 再涨 1 GB，仍可能再触发整机 OOM。
- **build_reps 阶段的写放大**：每个种子要写 u 矩阵约 5 GB（train 1.6 + valid 0.53 + test 2.93），
  脏页与页缓存同时抬升，是本单剩余阶段里**内存压力最高的时刻**。
- 应对：顺序跑 + 看门狗 + `RUN_STATE.md` 续跑指引（任何一次中断后按指引续跑，不重新规划）。

### 13.5 误判纠正：面板读放大在**顺序遍历**下不成立（build_reps 不会跑成百小时）
- **一度担心的结论（错误）**：以为 `build_reps` 的 `perm = np.lexsort((di, si))` 是**日期序**，
  在面板布局 (stock, date, feat) 下会造成随机散射访问 → 按 §11.1 的 129× 放大推算，
  test 切分要读 ~7.4TB、跑十几小时。
- **纠正**：`np.lexsort` 的**主键是 keys 序列的最后一个**，`np.lexsort((di, si))` =
  **先按 si（股票）主序、再按 di（日期）次序** → 实际是 **stock-major**。
  面板布局 (stock, date, feat) 下**同一只股的连续日期在磁盘上连续**，
  stock-major 遍历 → 每只股票一次连续读。
- **实测（seed42，epoch0 验证期，2026-11-25 16:32–16:41）**：
  valid 上下文区间 = 日期下标 [2063, 2671] = 609 天 × 5783 股 × 160B ≈ **561MB**；
  实测读盘增量 **1.4GB**（≈2.5×，来自 context / future / prior 三趟各自触发 readahead），
  **不是 129×**。验证 1039 批耗时 ~430–500s，属**计算受限**（编码器前向 ~1245 样本/s）。
- **结论**：`build_reps` 的 train/valid/test 三趟读盘总量约 1.2–2GB，
  时间由编码器前向的浮点计算主导（train 1.59M 样本 ≈ 21 min、valid 531K ≈ 7 min、
  test 2.95M ≈ 40 min），**不需要改布局、不需要额外暂存 valid/test**。
- **教训**：`np.lexsort((a, b))` 的主键是 `b`——与直觉相反；
  以后凡涉及"遍历顺序决定 I/O 局部性"的判断，**先读 numpy 文档确认主键顺序**，
  不要凭直觉推算放大倍数。

### 13.6 加线程提速的 A/B：**负结果**（不加线程）
- **动机**：训练进程瞬时 CPU 仅 447%（6 线程里 5 个 torch 工作线程各约 80% 忙），
  机器 `vmstat` 显示 us 54% / **id 23%** / wa 15% → 看似还有 2 个线程的余量，
  估「换 8 线程可省 ~1.8 小时」。
- **A/B 实测**（`scripts/work566_train.py --bench`，batch 64，纯计算微基准，与正式训练同机同时段）：
  | threads | sec_per_batch | samples_per_sec |
  |---|---|---|
  | 6 | **0.618** | **103.6** |
  | 8 | **2.208** | **29.0** |

  → **8 线程比 6 线程慢 3.6 倍**。
- **解释**：整机 loadavg 15.54 / 8 vCPU（282 个 S、103 个 I 态线程）已严重超订；
  8 线程下每线程分到的碎片更小，同步与调度开销占主导，线程数越多反而越慢。
- **结论**：**不重启、不加线程**，维持 `--threads 6`。种子链式守护里的 seed2024 同样用 6 线程。
- **附带证据（线程数不影响数值）**：seed42 在 **4 线程双进程**与 **6 线程单进程**两种配置下，
  `upd50/100/150/200` 的 `L_anc/L_rev` **逐位相同**（66.6294/53.4636 → 50.7801/35.0353），
  说明本机 CPU 浮点结果与线程数无关 —— 该结论同时支撑「§13.3 顺序跑」与「跨配置可比」。

### 13.7 build_reps 的 u 写回是**散写** → read-modify-write + 128KB readahead 放大（阻断级）
- **现象**：seed42 表征训练跑完（4000 upd / 6111s）后进入 `build_reps`，**训练切分 2,675 行就花了 38 秒**；
  进程瞬时 CPU 只有 **77%**（验证期是 447%）→ 主线程长期 **D 态** → 典型 I/O 受限。
- **取证**：
  | 指标 | 实测 |
  |---|---|
  | `rchar` 增量 | **0 KB / 25s**（没有 read()/pread() syscall） |
  | `read_bytes` 增量 | **108 MB / 25s（4.3 MB/s）** |
  | `u_seed42_train.npy` 映射驻留 | **8.3 MB / 1.72 GB**（脏页被迅速写回驱逐） |
  | 面板 `feat.npy` 映射驻留 | ≈0（面板读全部由 tmpfs 承担：835 MB 驻留） |
- **根因**：`build_reps` 里 `idx_all` 是**日期序**，而处理顺序 `perm = np.lexsort((di, si))` 是
  **stock-major**（`np.lexsort` 主键是最后一个 key）→ `u[pos]` 的**行号与处理顺序不一致** → 每次写 992 B
  落在不同 4KB 页 → 触发 **read-modify-write**，且内核默认 **128KB readahead** 把每次缺页放大成
  128KB 读 → 1.44M 次写 ≈ **184 GB 读**。
- **外推**：实测 2.9–14 ms/行 → 真实 train 切分（1.44M 行）≈ **5.6 小时**，
  加 valid/test → build_reps 合计 **8–9 小时**（不可接受）。
- **处置（只改行序，不改任何取值）**：`idx_all` 改为按 **(stock, date)** 排序 →
  `perm` 退化为**恒等置换**（代码里加了 `assert np.array_equal(perm, np.arange(len(perm)))`）→
  ① 面板读取仍是 stock-major 连续读；② **u 写回变成连续写**。
- **效果（同一冒烟参数对照）**：train 切分 **38 s → 约 3 s**；valid 15 s → 10 s；test 44 s → 39 s
  （valid/test 由**面板读盘**主导，故改善有限）。表征验证损失 140.0409 两次**完全相同**。
- **取值不变的证明（逐位）**：同参数跑旧实现与新实现各一次，按 (stock, date) 对齐后比较
  `y` 与 `pred`：**train / valid / test 三个切分全部 max|Δ| = 0.000e+00（逐位相同）**。
  样本集合、各日期样本数、y 多重集亦完全一致 → **只改行序，未改任何一个比特**。
- **下游不受影响**：读出按日期分组、回测与独立复算均按日期分桶（`dates_sorted = np.unique(date)`），
  与行序无关；npz 里 `idx/stock/date/y` 与 `pred` 同序保存 → 自洽。
- **附带**：新增 `--resume-rep`（表征 checkpoint 已存在则跳过表征训练）。
  checkpoint 即**按验证损失选出的最优权重**（`train_representation` 末尾写的是 `best[1]`），
  故续跑与完整跑一遍**完全等价**，只是省掉重训时间（本单省下 6111 s）。
- **教训**：`(stock, date)` 这种"行序"在内存里无所谓，但落到**按行寻址的 memmap** 上，
  行序 = 写放大；**矩阵的行序必须与写入顺序一致**，否则每次写都退化成 read-modify-write。
