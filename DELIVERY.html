一、做了什么

稳定代码与调度

代码固定在 /srv/share/quantdb/code/quant-lab，用 git 分支管理。四个 service 直接执行仓库里的 wrapper，不再依赖会被清理的任务 workdir。

systemd 单元和 wrapper 都在 db/timers/，已安装到 ~/.config/systemd/user/。

增量而不是全量

行情按 max(trade_date)+1 推进；收盘前以上一交易日为终点，避免把未发布数据写成空分区。财务用 disclosure_date(actual_date=...) 找代码，再按公告日与报告期窗口抓取。

装载按 DuckDB 水位补装所有更晚的 raw 分区；重复装载使用主键 upsert，行数不变。

图 1｜数据与调度。定时器只负责触发；抓取、合并和装载都在稳定仓库的 Python ETL 中。失败进入 wrapper 的统一告警路径，冷备独立校验源目录。

四、遗留与需要确认

  • 政策历史欠账。首次对账时库内样本很少，周一对账单轮默认补抓 200 条，remaining 逐周下降；不是丢数据，是有界补抓。
  • 周一财务体量。非报告期周一处理最近 7 天实际披露的代码，披露密集时可能跑几十分钟。
  • borg 既有故障。backup-nightly.service 在本单之前就是 failed；本单把 quantdb 冷备放在前面并加了失败告警，borg 原始错误仍需单独处理。
  • 非阻塞审查建议。weekly 锁冲突时的报告跳过、provisional 周报统计、空分区重复写、同尺寸损坏文件的哈希校验，均记录在 03-review-round5.md，不阻塞本次交付。
  • 时区。timer 依赖主机本地时区；当前主机为 Asia/Shanghai，list-timers 显示 CST。
  • 用量。平台 multica issue usage 返回全 0，无法给出真实 token；本轮审查进程自报 token 较高，但这不是平台计量。
